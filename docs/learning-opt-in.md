Run `flow learn` from a Git repository (including a nested directory), or from an existing plain directory; Git is optional for plain directories. First use registers that project for existing due/scheduled learning; repeat use shows the project name, learning enabled/paused state, verified outcome and recommendation counts, and feedback wait state without resetting or resuming it. This does not install a scheduler or initiate network/model calls. Use the existing learner `due` entrypoint to run scheduled work with its normal offline/live controls.

`flow learn status`, `results`, and help never register a project. Explicit `onboard`, `check`, `feedback`, `pause`, and `resume` remain available. `flow learn unregister` removes this project's registration and reports the existing private retention action; `--retention retain_redacted` explicitly selects the alternative. Use `--repo` for a plain directory other than the current one. Project identities are bound to canonical paths; use the same shared storage root across invocations.

An optional private `.flow/learner-profile.json` uses the existing ProjectProfile fields and must contain `root_path` matching this repository's absolute canonical path. Curate mission, goals, capabilities, private terms and finite budget there. Generic registration derives private mission, goals and capabilities from the existing bounded docs fallback. Unauthored docs never supply public search concepts. Explicitly curated sanitized public concepts, export permissions and retention remain intact; otherwise public queries and shared exports default off. It always keeps execution paused. Flow-specific capabilities and CR-1 rules apply only to Flow checkouts. Generic profiles retain their own finite model budgets even when Flow has a historical unlimited grant. Flow-run implementation routing is independent.

The due runner automatically reads `.flow/verified-outcomes.jsonl` only for learning-enabled projects. Each line must contain `project_id`, `assessment_id`, `external_experiment_ref`, `status` (accepted/rejected/inconclusive), `baseline_summary`, `outcome_summary`, `evaluator`, and `verified: true`. These are owner-verified references to actual experiments, not verification commands. The referenced assessment must belong to this project. Repeated experiment references are idempotent; conflicting references fail validation before any batch write. Imports are limited to 1 MiB and 1,000 records, read before the shared schedule lease. A project import failure is reported in `outcome_import_errors` and does not stop other projects. Status reads never import this file. Outcomes enter the existing outcome store and negative-outcome assessment consumer with explicit project-bound owner-attestation provenance. Ordinary outcome references have no ranking authority.

Recommendations automatically rank matching goal/capability tracks using accepted versus rejected outcomes against documented baselines, after at least two distinct experiments on proposals with validated citations. The same scores prioritize comparable pending deep assessments within each project, after existing continuation and feedback priorities. Scores are calculated once per project per pass. Otherwise recommendation ranking remains newest first. The bounded score is reported as `verified_outcome_rank`; inconclusive outcomes do not count. New contrary evidence reverses the preference; paused projects use baseline ordering. This changes learner recommendation priority, not application code or business strategy, and does not claim measured performance gains. No usable evidence means no rank adjustment.

Identity bindings retain only the canonical root digest across unregister, independently of private retention. Re-registration under that identity requires the same canonical root. Revisions cannot move roots. Legacy tombstones that predate identity bindings and contain no root cannot be safely rebound; registration reports that a new identity is needed. The `flow_learning` unlimited grant is restricted to its registered Flow owner at the canonical engine repository, including shared dispatch target accounting; unrelated historical grant scopes keep their existing semantics. No financial decisions or execution permissions change.
